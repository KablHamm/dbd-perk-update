# Perk Picker delta

This repository is the data feed for the **Perk Picker** app on the rabbit r1.
It exists so the app can pick up Dead by Daylight perks released after the
build, with no computer switched on and nobody remembering to do anything.

## What is in here

| File | What it is |
| --- | --- |
| `perks-update.json` | The delta. Only the perks the app does not already bundle. |
| `baseline.json` | Which 330 perks the app already bundles - side and name only. All the scraper needs to tell a new perk from an old one. |
| `tools/build_perk_update.py` | The scraper. Reads the wiki's rendered HTML and rewrites `perks-update.json`. |
| `tools/delta_changed.py` | Says whether a rebuild actually changed the perk list. |
| `.github/workflows/refresh.yml` | Runs the scraper daily and commits the delta when it changed. |

## How the device reads it

The r1 fetches

```
https://raw.githubusercontent.com/KablHamm/dbd-perk-update/main/perks-update.json
```

`raw.githubusercontent.com` sends `Access-Control-Allow-Origin: *`, so the
device can fetch it. The wiki itself cannot be fetched from the device at all:
its perk tables are generated by a Lua module, and it answers with no CORS
header whatsoever. **This repository has to be public** - a private repository
is not served from that address without a token, and the app has nowhere to
put one.

The app tries that address first and falls back to the `perks-update.json`
shipped inside it. If this repository is deleted, renamed, made private, or
simply unreachable, the app carries on working from the copy it already has;
it just stops seeing new perks.

## Why this exists

The app is served from a host that OS3 fills by reading files off a PC. With
that PC off there is no way to publish to it, so a refresh tied to that
address needs the PC switched on. This repository is a plain web host that a
scheduled run can rewrite by itself, which is what makes the refresh runnable
with the PC off.

## The daily run

GitHub Actions runs `tools/build_perk_update.py` at 06:17 UTC, daily and also
on demand from the Actions tab. The scraper is idempotent: it always rewrites
the whole delta from the wiki and the baseline, so re-running it never
duplicates a perk and never removes one the app already has. If the perk list
came out the same, `delta_changed.py` exits 0 and nothing is committed.

Run it by hand from a checkout with Python 3:

```
python tools/build_perk_update.py
python tools/delta_changed.py <published.json> perks-update.json
```

`build_perk_update.py` prints one line per new perk and writes the file.
`delta_changed.py` exits 0 for unchanged and 1 for changed, so it can be used
directly as a commit guard.

## Adding a new perk

It needs no action at all - the next daily run finds it. To force it sooner,
use **Run workflow** on the Actions tab.
